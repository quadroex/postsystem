# Вимоги до системи

Система обліковує доставку посилок між поштовими відділеннями: реєстрацію клієнтів, приймання, перевезення, відстеження, оплату та вручення. Адресна доставка до дверей у межі проєкту не входить.

## Функціональні вимоги

| Код | Вимога | Сутності |
|---|---|---|
| R01 | Зберігати працівника, від імені якого виконано операцію. | `app_users` |
| R02 | Реєструвати відправників та одержувачів, їхні телефони й електронні адреси. | `customers` |
| R03 | Вести довідники країн, міст і поштових адрес відділень. | `countries`, `cities`, `addresses` |
| R04 | Зберігати відділення з унікальним кодом, адресою та ознакою роботи. | `branches` |
| R05 | Визначати вид послуги та чинний тариф: базову вартість, ціну за кілограм, страхову ставку й граничну вагу. | `service_types`, `tariffs` |
| R06 | Створювати відправлення з унікальним номером відстеження, відправником, одержувачем, двома різними відділеннями та оголошеною вартістю. | `shipments` |
| R07 | Додавати до відправлення пакунки з описом, вагою й трьома розмірами. Вага та розміри мають бути додатними. | `parcels` |
| R08 | Обчислювати ціну за тарифом послуги, сумарною вагою пакунків та оголошеною вартістю. | `tariffs`, `shipments`, `parcels` |
| R09 | Зберігати поточний стан відправлення та історію подій із часом, відділенням і працівником. | `shipment_statuses`, `shipments`, `shipment_events` |
| R10 | Реєструвати нумеровані спроби вручення з результатом `failed` або `delivered`. Номер спроби в межах відправлення не повторюється. | `delivery_attempts` |
| R11 | Зберігати додатні суми оплат, спосіб оплати, час і працівника. Непорожній платіжний референс має бути унікальним. | `payment_methods`, `payments` |
| R12 | Вести транспорт із унікальним реєстраційним номером і додатною вантажністю. | `vehicles` |
| R13 | Визначати маршрут між різними відділеннями та впорядковані зупинки. Відділення й порядковий номер у межах маршруту не повторюються. | `transport_routes`, `route_stops` |
| R14 | Планувати рейси з маршрутом, транспортом і часом відправлення. Час прибуття, якщо вказаний, має бути пізнішим. | `transport_runs` |
| R15 | Призначати багато відправлень одному рейсу; кожне відправлення може бути призначене лише одному рейсу. Зберігати час і автора завантаження. | `run_shipments` |
| R16 | Приховувати архівовані клієнти, адреси, відділення та відправлення зі звичайних вибірок, зберігаючи пов’язані історичні записи. Дозволяти відновлення. | `customers`, `addresses`, `branches`, `shipments` |
| R17 | Для змінюваних сутностей фіксувати час і автора створення, останньої зміни та архівування. Записувати попередні й нові дані до журналу. | Чотири таблиці R16, `audit_log` |
| R18 | Створювати відправлення, його пакунки та пов’язані операції в одній транзакції. У разі помилки відкотити всі зміни. | `customers`, `shipments`, `parcels`, `payments`, `shipment_events` |

## Soft delete та аудит

| Таблиці | Поля | Правило |
|---|---|---|
| `customers`, `addresses`, `branches`, `shipments` | `created_at`, `created_by` | Час і автор створення. |
| Ті самі | `updated_at`, `updated_by` | Час і автор останньої зміни, включно з архівуванням та відновленням. |
| Ті самі | `deleted_at`, `deleted_by` | Обидва `NULL` для активного запису; обидва заповнені для архівованого. |
| `audit_log` | `entity_name`, `entity_id`, `operation`, `changed_at`, `changed_by`, `old_data`, `new_data` | Історія `insert`, `update`, `soft_delete`, `restore`. Дані запису зберігаються як `jsonb`. |

Користувач застосунку працює через процедури та представлення. Фізичне видалення чотирьох таблиць із soft delete забороняється тригером. Зовнішні ключі зберігають історичні зв’язки після архівування; каскадне видалення не використовується.

Архівування батьківського запису не означає архівування дочірніх. Історичне відправлення зберігає посилання на свого клієнта чи відділення. При створенні нового відправлення перевіряються активність учасників і доступність відділень.

Операції виконуються від імені активного `app_users`. Автор передається процедурі; тригери виставляють аудит на боці БД. У `parcels`, `transport_runs`, `run_shipments` зберігається автор створення/завантаження; у подіях, спробах вручення та оплатах — автор реєстрації.

## Обмеження реалізації

- СУБД — PostgreSQL, об’єкти проєкту розміщено у схемі `postal`.
- Коди, номери відстеження, поштові індекси, суми та розміри перевіряються обмеженнями БД.
- Первинні ключі сутностей — UUID або числовий ідентифікатор; `run_shipments` має складений PK.
- У зв’язку послуги з тарифом діє 1 → 0..1; таблиця зберігає один чинний тариф послуги.
- Індекси мають включати щонайменше два різні методи доступу PostgreSQL.
- Прикладний код застосовує Repository + Unit of Work; читає представлення та змінює дані викликами процедур. Прямі запити до предметних таблиць для прикладної ролі закрито.

Повний перелік полів і ключів наведено у [каталозі сутностей](entities.md), зв’язки — на [ER-діаграмі](design/er.md).
